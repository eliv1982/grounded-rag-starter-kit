# grounded-rag-starter-kit

**Reusable RAG starter kit for source-grounded vertical AI assistants.** It provides a domain-neutral core for
deterministic evidence selection, grounded generation, cache/index lifecycle integrity, and local or hosted
OpenAI-compatible execution. Domain behavior is supplied through corpus manifests and optional profiles without
modifying the core.

Reference verticals: neutral synthetic examples (`sample_corpus/`, `examples/equipment_manual/`) and one legal
reference vertical (`examples/independent_guarantees/`).

Not a product and not an enterprise framework: answers are generated by a model from retrieved fragments, and source
references in them are not verified automatically. Domain-specific disclaimers are supplied by a vertical's profile.

---

## О проекте

Репозиторий — учебно-портфолио starter kit для ассистентов, отвечающих строго по источникам. Ядро (`app_core/`) не содержит ни корпуса,
ни предметной лексики: вертикаль подключается **данными** (манифест корпуса + необязательный профиль), а не правками ядра.
Предметная специфика (разбиение документов на разделы, подписи источников, доменные формулировки промпта, датасет оценки)
живёт в вертикали и отделена от технического ядра.

Что доказано кодом и тестами:

- ядро нейтрально (тест на отсутствие предметной лексики и на направление зависимостей: `tests/test_core_boundary.py`);
- нейтральная синтетическая вертикаль (`examples/equipment_manual/`, вымышленная кофемашина) работает через то же ядро
  без изменений в нём (`tests/test_verticals.py`);
- юридическая референс-вертикаль (`examples/independent_guarantees/`, независимые гарантии по российскому праву) — один из примеров
  доменного профиля: её структурные правила (статьи и параграфы, русские подписи источников) и юридические формулировки промпта
  вынесены из ядра в её профиль; профиль проверяется тестами на синтетическом тексте (сами тексты приватны и в репозитории отсутствуют).

Чем проект **не** является: не enterprise-решением, не «универсальным AI-фреймворком», не провайдер-универсальным
(нужен OpenAI-совместимый API) и не полностью приватным в hosted-режиме. Ответы модели не заменяют экспертной проверки по источникам.
См. «Известные ограничения».

## Быстрый старт

Каноническая версия Python — **3.11** (проверено на 3.11.9). Другие версии не тестировались и не заявляются как поддерживаемые.

### 1) Окружение

**Windows (PowerShell):**

```powershell
py -3.11 -m venv venv
.\venv\Scripts\Activate.ps1
```

**Linux/macOS:**

```bash
python3.11 -m venv venv
source venv/bin/activate
```

### 2) Зависимости

Зависимости разделены по файлам; `constraints-py311.txt` фиксирует протестированные версии для Python 3.11.

```bash
# Рантайм + тесты (рекомендуется для разработки):
pip install -r requirements-dev.txt -c constraints-py311.txt

# Только рантайм (CLI + web):
pip install -r requirements.txt -c constraints-py311.txt

# Опционально: стек RAGAS для evaluate_ragas.py (поверх рантайма):
pip install -r requirements-eval.txt -c constraints-py311.txt
```

### 3) Настройка окружения

Выберите профиль и скопируйте значения в файл `.env` **в корне репозитория**:

- `.env.local.example` — локальный Ollama-режим;
- `.env.hosted.example` — hosted OpenAI-compatible режим (по умолчанию `https://api.openai.com/v1`);
- `.env.example` — объединённый reference-шаблон.

`.env` читается только из корня репозитория (родительские каталоги не просматриваются). Переменные, уже заданные в окружении ОС,
имеют приоритет над значениями из `.env`. `.env` и `.env.*` игнорируются git, кроме шаблонов `*.example`.

### 4) Корпус (вертикаль)

Корпус задаётся явно — JSON-манифестом в `RAG_CORPUS_CONFIG` (путь от корня репозитория). Без него приложение не стартует:
манифест нужен при каждом старте, чтобы проверить индекс на соответствие корпусу.

```env
RAG_CORPUS_CONFIG=sample_corpus/corpus.json
```

`sample_corpus/` — крошечный синтетический пример (вымышленная компания) без профиля, то есть «голое» ядро. Приватные материалы кладите
в `raw_sources/`, `knowledge_base/` или `data/` — их содержимое игнорируется git.

Индексация при первом запуске и при каждой пересборке вызывает embeddings-API выбранного провайдера. Web-интерфейс создаёт
пайплайн один раз при старте, поэтому пересборка происходит при запуске, а не при первом вопросе.

### 5) Запуск

```bash
python app.py                      # консольное приложение
uvicorn web.app:app --port 8010    # web-интерфейс, http://127.0.0.1:8010
```

Web-интерфейс не имеет аутентификации и рассчитан на локальный запуск; не публикуйте его порт во внешнюю сеть.

## Вертикали и профили

Вертикаль — это каталог с документами и одним манифестом. В репозитории три варианта:

| Каталог | Что показывает |
| --- | --- |
| `sample_corpus/` | нейтральный корпус без профиля (поведение ядра по умолчанию) |
| `examples/equipment_manual/` | вторая, нейтральная синтетическая вертикаль: ~10 строк конфигурации, без кода |
| `examples/independent_guarantees/` | юридическая демо-вертикаль (тексты не в репозитории, см. её README) |

### Добавить свою вертикаль (без правок `app_core/`)

1. Положите документы (UTF-8 `.txt`) в каталог, например `examples/my_vertical/`.
2. Создайте `corpus.json` с `entries` и, при необходимости, `profile`:

```json
{
  "profile": {
    "name": "equipment_manual",
    "system_prompt_extra": "You answer questions about the Aurora X2 machine for service staff. Quote error codes exactly.",
    "section_boundaries": { "manual": "(?m)^(?=Procedure\\s+\\d+\\.)" },
    "kind_labels": { "service_manual": "service manual" },
    "chunk_header": "[{kind_label}: {source_display}]\n[Procedure: {heading}]\n\n"
  },
  "entries": [
    { "path": "manual.txt", "source": "aurora_x2_manual", "source_display": "Aurora X2 Service Manual",
      "source_kind": "service_manual", "doc_type": "manual" }
  ]
}
```

3. Укажите `RAG_CORPUS_CONFIG=examples/my_vertical/corpus.json`, запустите приложение — индекс построится при старте.
4. Необязательно: `eval.json` для оценки (см. ниже).

Поля профиля (все необязательны; профиль — это **данные**, а не код, поэтому он автоматически входит в отпечатки индекса и кеша):

| Поле | Действие |
| --- | --- |
| `name` | идентификатор вертикали (показывается в `stats`) |
| `system_prompt_extra` | доменные инструкции, **добавляемые после** основных правил grounding; заменить эти правила нельзя |
| `section_boundaries` | `doc_type` → regex начала нового раздела (нулевой ширины); без записи документ не делится на разделы |
| `kind_labels` | `source_kind` → подпись в заголовке чанка |
| `chunk_header` | шаблон заголовка чанка: `{source_display}`, `{kind_label}`, `{heading}` |
| `sentence_language` | язык pysbd для деления длинных абзацев (по умолчанию `en`) |

Профиль задаётся владельцем репозитория и доверяется как манифест корпуса; это не пользовательский ввод. Ограничения:
`system_prompt_extra` — до 4000 символов; опечатки в ключах профиля и неизвестные поля шаблона дают явную ошибку при старте.

## Режимы работы

Чат и эмбеддинги идут через **один** OpenAI-совместимый endpoint (`LLM_API_KEY`, `LLM_BASE_URL`). Отдельного embeddings-провайдера нет.

### Local (например, Ollama)

```env
LLM_API_KEY=local-placeholder
LLM_BASE_URL=http://localhost:11434/v1
RAG_CHAT_MODEL=gemma3:4b
RAG_EMBEDDING_MODEL=bge-m3
RAG_CHROMA_PATH=runtime/chroma_db_local_bge_m3
RAG_CORPUS_VERSION=local-bge-m3-v1
```

### Hosted OpenAI-compatible

```env
LLM_API_KEY=your-api-key
LLM_BASE_URL=https://your-openai-compatible-endpoint/v1
RAG_CHAT_MODEL=gpt-4o-mini
RAG_EMBEDDING_MODEL=text-embedding-3-small
RAG_CHROMA_PATH=runtime/chroma_db_hosted_text_embedding_3_small
RAG_CORPUS_VERSION=hosted-text-embedding-3-small-v1
```

Рекомендации: держите локальную и hosted векторные базы в разных `RAG_CHROMA_PATH` (относительный путь отсчитывается от корня
репозитория, как `.env` и манифест корпуса, а не от текущего каталога; абсолютный используется как есть). Устаревшие `OPENAI_API_KEY` / `OPENAI_BASE_URL`
по-прежнему работают, **но только если не задан `LLM_API_KEY`**: при новой конфигурации забытый `OPENAI_BASE_URL` игнорируется и не
перенаправит запросы на другой endpoint. Имена `OPENAI_TIMEOUT`, `OPENAI_MAX_RETRIES`, `OPENAI_EMBED_RETRIES` сохранены по историческим
причинам и относятся к любому OpenAI-совместимому endpoint.

Основные параметры: `RAG_RAW_TOP_K`, `RAG_MAX_DISTANCE`, `RAG_FINAL_TOP_K` (устаревший `RAG_TOP_K`), `RAG_MAX_TOKENS`, `RAG_TEMPERATURE`,
`RAG_CHUNK_SIZE`, `RAG_CHUNK_OVERLAP`, `RAG_MIN_CHUNK_LEN`, `RAG_EMBED_BATCH_SIZE`, `RAG_COLLECTION_NAME` (по умолчанию `rag_collection`).

## Retrieval и grounding

Один quality pass — `select_context` (`app_core/retrieval/selection.py`); его же вызывают пайплайн и диагностические скрипты.
Порядок результатов поиска сохраняется:

1. **Raw retrieval** — расширенный набор кандидатов (`RAG_RAW_TOP_K`, по умолчанию `10`).
2. **Distance и cutoff** — остаются фрагменты с корректным (числовым, конечным) расстоянием не выше `RAG_MAX_DISTANCE` (по умолчанию `0.44`).
   Отсутствующий, `None`, NaN и нечисловой distance не проходят.
3. **Dedup по содержимому** — удаляются только точные дубли текста (после нормализации Unicode NFC и пробелов), остаётся фрагмент с лучшим
   рангом. Разные фрагменты одного источника или раздела не схлопываются.
4. **Final clamp** — не более `RAG_FINAL_TOP_K` (по умолчанию `5`). Слабые результаты не добавляются: подходящих фрагментов может быть меньше или не быть вовсе.

Если подходящих фрагментов нет, LLM **не вызывается**: пользователь получает детерминированный ответ о недостаточности данных (без ссылок
на источники; такой ответ не кешируется). Web-интерфейс в этом случае пишет «Недостаточно подходящих источников — модель не вызывалась».

Фрагменты передаются в prompt внутри тегов `<retrieved_fragment number="N" ...>`; системный prompt и инструкции требуют считать их
недоверенными справочными данными, не выполнять содержащиеся в них указания и указывать на противоречия между источниками. Это снижает
риск, но не гарантирует поведение модели; ссылки на источники в тексте ответа пишет модель, и они **не проверяются автоматически**.
Web-интерфейс подписывает карточки как «извлечённые фрагменты: контекст, переданный модели» и нумерует их так же, как фрагменты в prompt.

Системный prompt = основные правила ядра + `system_prompt_extra` вертикали (добавляется после них и не может их заменить).

## Кеш и жизненный цикл индекса

**Кеш ответов.** Ключ — SHA-256 от «отпечатка конфигурации ответа» и нормализованного вопроса. В отпечаток входят: версия корпуса
`RAG_CORPUS_VERSION` и отпечаток корпуса; чат-модель, `RAG_TEMPERATURE`, `RAG_MAX_TOKENS` и провайдер/base URL (только односторонний хэш
нормализованного URL; ключи API в отпечаток не попадают); embedding-модель, chunking-настройки и **профиль вертикали** (правила нарезки
и хэш `system_prompt_extra`); `RAG_RAW_TOP_K`, `RAG_FINAL_TOP_K`, `RAG_MAX_DISTANCE`; явные версии в `app_core/lifecycle.py`
(`PROMPT_VERSION`, `RETRIEVAL_SELECTION_VERSION`, `CHUNKING_VERSION`, `INDEX_MANIFEST_VERSION`, `CACHE_FINGERPRINT_VERSION`).
Смена любого значения даёт промах кеша, записи прежней конфигурации остаются нетронутыми. Версии-константы меняются вручную при изменении
prompt, правил отбора или алгоритма нарезки — автоматического определения нет. TTL нет. Ошибка модели или пустой ответ не кешируются.

**Индекс Chroma.** Непустая коллекция сама по себе не считается доверенной: вместе с ней в метаданных хранится манифест (версия манифеста,
версия корпуса, отпечаток корпуса, embedding-модель и провайдер, chunk size/overlap/min length, отпечаток профиля, версия алгоритма нарезки,
число чанков и состояние `incomplete`/`complete`). При каждом старте (CLI и web, до первого запроса) он сверяется с конфигурацией.
Коллекция пересобирается автоматически, если манифеста нет, индексация была прервана, число чанков не сходится или изменились корпус,
embedding-модель/провайдер, chunking или профиль; причина пишется в лог без секретов и содержимого корпуса. Пересборка затрагивает только
коллекцию приложения. Состояние `complete` ставится только после записи всех чанков; прерванная индексация перестраивается с нуля.
Корпус читается и нарезается до удаления старого индекса, поэтому ошибка в корпусе не стирает рабочий индекс.

**Отпечаток корпуса** — SHA-256 от записей манифеста (`source`, `source_display`, `source_kind`, `doc_type`, имя файла) и содержимого
каждого файла (с нормализованными переводами строк). Он не обнаруживает изменения файлов, не перечисленных в манифесте, и перемещение
каталога (важны только имя файла и содержимое).

Заголовок чанка ограничен половиной `RAG_CHUNK_SIZE`: слишком длинный заголовок сначала укорачивает заголовок раздела, а если и этого
мало — чанк получает только тело (источник остаётся в метаданных). Так при маленьком chunk size или длинном названии источника тело чанка
не вырождается в обрезки.

Единое имя коллекции для CLI, web, evaluation и скриптов — `RAG_COLLECTION_NAME` (по умолчанию `rag_collection`).

## Приватность и поток данных

- **Локальные файлы** (всё в `runtime/`, `.env`, `data/` — игнорируется git): Chroma хранит **тексты чанков** корпуса и эмбеддинги,
  SQLite-кеш `runtime/rag_cache.db` — **текст вопросов, ответы и найденный контекст**. Всё в открытом виде, без шифрования и без TTL;
  записи прежних конфигураций не удаляются автоматически. Очистка кеша — команда `clear` в CLI или удаление файла.
- **Hosted-режим** (`LLM_BASE_URL` не задан или указывает на внешний шлюз): каждый вопрос и найденные фрагменты отправляются провайдеру
  чата; тексты чанков при индексации и каждый вопрос при поиске — провайдеру эмбеддингов (это тот же endpoint). Оператор шлюза их видит.
  Hosted-режим не является приватным.
- **Local OpenAI-compatible режим** (`LLM_BASE_URL=http://localhost:11434/v1` и т. п.): те же данные уходят только на настроенный endpoint.
  Анонимная телеметрия Chroma отключена кодом.
- **Оценка качества** отправляет вопросы, найденный контекст, ответы и эталоны модели-судье. По умолчанию судья — тот же endpoint, что и у
  приложения; другой (например, hosted) судья включается только явной парой `RAG_EVAL_JUDGE_BASE_URL` + `RAG_EVAL_JUDGE_API_KEY`.
  Случайно заданный `OPENAI_API_KEY` судью не выбирает.
- **Пересборка индекса**: первый запуск, отсутствие/несовместимость манифеста индекса, смена корпуса, embedding-модели, chunking или
  профиля вызывают повторные embeddings-запросы по всем чанкам (в hosted-режиме платные, и тексты чанков уходят провайдеру).
- **Логи**: пайплайн не печатает текст вопроса (только его длину и счётчики). CLI выводит вопрос и ответ в ваш терминал, web-сервер
  показывает текст ошибок в странице; стек запуска (systemd, Docker, терминал) может сохранять stdout сам — учитывайте это.

## Оценка качества (опционально)

Не входит в рантайм, CI и quality gate. Нужен `requirements-eval.txt`; каждый запуск делает вызовы модели-судьи (в hosted-режиме платные).

```bash
python evaluate_ragas.py --dataset examples/equipment_manual/eval.json
```

- Датасет принадлежит вертикали и указывается **явно**: JSON `{"cases": [{"question": ..., "ground_truth": ...}]}`. Встроенного набора нет.
  Корпус и профиль берутся из `RAG_CORPUS_CONFIG`: он должен соответствовать датасету.
- Судья: по умолчанию endpoint приложения (`LLM_API_KEY`/`LLM_BASE_URL`), модель — `RAG_EVAL_JUDGE_MODEL`, `--judge-model` или `RAG_CHAT_MODEL`.
  Отдельный судья — только парой `RAG_EVAL_JUDGE_BASE_URL` + `RAG_EVAL_JUDGE_API_KEY` (ключ приложения туда не отправляется).
  Перед запуском печатается, какому endpoint уйдут данные.
- Анонимная телеметрия RAGAS по умолчанию отключена (`RAGAS_DO_NOT_TRACK=true`, если вы не задали эту переменную сами); на выбор судьи это не влияет.
- Метрики (Faithfulness, Context precision, Context utilization) считает LLM-судья: это ориентир для сравнения конфигураций, а не доказательство корректности.

Детерминированную регрессию (отбор контекста, grounding, кеш, жизненный цикл индекса, профили) обеспечивают офлайн-тесты.

## Тесты и CI

```bash
pytest -q
```

Тесты работают офлайн: ключи API и сеть не нужны, провайдеры подменены заглушками (fake embeddings и fake chat). GitHub Actions
(`.github/workflows/ci.yml`) на Python 3.11 запускает `pip check`, compile/import sanity и `pytest`, а отдельная задача проверяет, что
необязательный стек оценки устанавливается и `evaluate_ragas` импортируется (оценка не запускается).

## Известные ограничения

- один endpoint для чата и эмбеддингов; один векторный store (Chroma); только векторный поиск без reranking и гибридного поиска;
- порог `RAG_MAX_DISTANCE` — эвристика, зависящая от embedding-модели, и подбирается вручную;
- только UTF-8 `.txt` корпус; PDF/DOCX не поддерживаются;
- встроенное детерминированное языковое поведение (ответ о недостаточности данных, заголовки и инструкции prompt) поддерживает только
  русский и английский: вопрос с кириллицей считается русским, любой другой — английским, поэтому вертикали на других языках получают
  английский вариант, пока это не расширено;
- web-интерфейс — один процесс, без аутентификации и многопользовательского режима;
- ссылки на источники в тексте ответа пишет модель, автоматической проверки цитат нет; prompt-injection снижается, но не исключается;
- хранилища (Chroma, кеш) и логи не шифруются; hosted-режим отправляет данные провайдеру;
- оценка — ручная, на LLM-судье; тексты юридической демо-вертикали приватны и в репозитории отсутствуют;
- индексы, построенные до появления манифеста/профиля, один раз пересобираются.

## Структура репозитория

```text
app_core/            # переиспользуемое ядро (карта модулей: app_core/README.md)
web/                 # FastAPI + Jinja2-шаблоны
examples/            # вертикали: independent_guarantees (юридическая), equipment_manual (синтетическая)
sample_corpus/       # нейтральный синтетический корпус без профиля
scripts/             # диагностика retrieval (read-only)
tests/               # офлайн-тесты
raw_sources/ knowledge_base/ data/   # приватные материалы (содержимое игнорируется git)
runtime/             # локальные Chroma и SQLite-кеш (игнорируется git)
```

Корневые `app.py`, `rag_pipeline.py`, `evaluate_ragas.py` — точки входа и оркестрация поверх `app_core`.
